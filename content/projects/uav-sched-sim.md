## 一句话

同一份任务轨迹（固定 seed 离线生成），换调度策略各跑一遍，用统一口径的指标回答两件事：**多级队列 + 动态权重 + 饥饿补偿 + 限流稳流 + 链路感知到底改善了什么，代价又是什么。**

这是《操作系统》课程实训工程，但它不是一份跑分脚本，而是三样东西叠在一起：

| 形态 | 是什么 | 入口 |
| --- | --- | --- |
| **仿真内核** | 纯 Python 多线程，13 个核心模块，可批处理复现实验 | `run.py all` |
| **桌面 3D 监控台** | pywebview + WebView2 + Three.js，真实 DEM 地形、30 架无人机、OS 透视镜 | `启动仿真软件.bat` / 13.9 MB 单文件 exe |
| **证据链** | CSV / JSON / MySQL 长表 / 10 类图表 / 结果界面 / Trace 回放 | `results/`、`📊 仿真结果` |

仿真内核只用标准库的 `threading` / `queue` / `concurrent.futures` / `statistics`，没有 asyncio，也没有调度框架；展示层才用 pywebview 与 Three.js。

## 四层映射：业务故障 → OS 原理

| 业务现象 | OS 原理 | 算法对策 |
| --- | --- | --- |
| 30 架机同时上传，地面站通道被打满 | 多生产者并发写就绪队列 → 队列溢出 / 背压 | 双队列隔离 + 容量上限 + 满则计数丢弃 |
| 心跳、GPS、告警长期传不上去 | 任务饥饿：低优先级等待时间无上界 | 饥饿检测（>15 s）+ 硬补偿通道 + 权重倍增 |
| 2 GB 点云排到队首，告警包全被堵住 | 队头阻塞 / 非抢占调度的护航效应 | 时间片 + 真实抢占，时间片随拥堵自适应 |
| 瞬时峰值把 CPU / IO 打满 | 资源耗尽 + 缺少并发限流 → 雪崩 | 并发许可 + 非阻塞准入，拿不到就留在队列错峰 |
| 弱网任务反复重传、抢走通道 | I/O 阻塞未降级 + 设备状态未参与调度 | 链路健康度并入权重，<40 降权 0.6，失败本地缓存 |
| 参数全部人工预设，换工况就失配 | 静态优先级 / 固定时间片 | 四因子权重实时计算，不依赖手工整定 |

每一行都有对应的可观测证据：队列深度、低优饥饿率、上下文切换与 P95 等待、限流与过载秒数、重传率与缓存条数、参数敏感性三组对照。具体字段名与 SQL 查询见 `docs/04` 与 `docs/05`。

完整 20 行映射（含代码位置与证据表）在仓库的 `docs/04-四层映射对照表.md`。

## 架构与关键实现

| 模块 | 职责 | 关键点 |
| --- | --- | --- |
| 仿真内核 | 30 个生产者线程按预生成时刻表提交任务，8 个工作线程消费 | `simulator.py`、`station.py` |
| 两级就绪队列 | 高优勘查 / 低优运维，各自计算拥堵度 | `queue_manager.py` |
| 任务状态机 | `NEW / READY / RUNNING / BLOCKED / CACHED / DONE / DROPPED` | `models.py` |
| 资源限流 | `OK / THROTTLE / REJECT_LARGE / QUOTA` 四种准入结果 | `resource_limiter.py` |
| 链路模型 | 时延、丢包、RSSI → 0~100 健康度，既折算带宽也决定失败概率 | `link_monitor.py` |
| 调度器 | 5 种经典策略 + `cross_node` 跨节点策略，统一接口 | `scheduler/*.py` |
| 分布式 | 每站一套线程池 / 队列 / 限流器，接入站 ≠ 算力站 | `station.py`、`mec.py` |
| 统计 | t 分位数、95% 置信区间、配对检验（零第三方依赖） | `statistics.py`、`replication.py` |
| 持久化 | MySQL 8 表 1 视图，数据库不可用时优雅降级为 CSV/JSON | `db.py`、`sql/01_schema.sql` |

关键约束是**控制变量**：任务到达与链路质量离线预生成为轨迹，5 种策略只回放同一条输入。测试里直接断言「同 `(code, seed)` 两次生成的轨迹逐元素相同」，并用 SHA-256 + 1e-9 精度守住单站基线。

## 六种调度策略

| 策略 | 一句话 | 角色 |
| --- | --- | --- |
| `fcfs` | 跨两个物理队列按全局到达顺序取 | 基线，暴露护航效应 |
| `rr` | 固定 500 ms 时间片，未完成回队尾 | 基线：能救饥饿，切换开销高 |
| `priority` | 高队列非空则低队列永远轮不到 | 反面教材：复现饥饿 |
| `mlfq` | 300 / 800 ms 分层时间片，低队列等超 1500 ms 升权 | 经典解法 |
| `dynamic` | `W = base × (w0 + αQ + βW + γL) × (1 − δS)`，叠加饥饿硬补偿与弱网降权 | 本方案主角 |
| `cross_node` | 继承 `dynamic`，站间再做最少连接 + 一致性哈希（64 虚拟节点） | 分布式扩展 |

`cross_node` 最初被写成独立的严格优先级调度，单站完整率只有 31.7%；重构为继承 `dynamic` 后回到 95.6%。**跨节点均衡解决的是站与站之间的不均，不能替掉站内的公平性与过载收敛。**

## 真实结果：先看峰值工况

PEAK 工况、seed 20261031，15 组中的 5 行（`results/summary.csv`）：

| 策略 | 吞吐（个/s） | 等待 高 / 低 | 低优饥饿率 | 业务完整率 |
| --- | ---: | ---: | ---: | ---: |
| FCFS | 15.14 | 34.3 / 24.1 s | 66.2 % | 55.8 % |
| RR | 25.13 | 25.9 / 2.26 s | 0.2 % | 92.4 % |
| 静态优先级 | 8.86 | **21.3** / 29.9 s | 65.7 % | 32.6 % |
| MLFQ | **26.04** | 26.0 / **1.11 s** | **0.0 %** | **95.9 %** |
| 动态权重 | 25.86 | 29.9 / 1.34 s | **0.0 %** | 95.2 % |

几件必须一起说的事：

- 静态优先级把 8 个槽位几乎全给了勘查任务：高优等待最低（21.3 s）、资源利用率最高（72.6%），但低优饥饿率 65.7%，**这就是 PDF 痛点④的教科书式复现**。
- FCFS 并不"保护弱者"：大任务护航让告警小包排在巨量数据后面，饥饿率同样 66.2%。
- 动态权重用 1443 次上下文切换（比 MLFQ 的 2135 少 32%），维持了同一档吞吐与完整率，并保持零饥饿；代价是高优等待比 MLFQ 更长——它愿意让低优任务先过。

## 最值得看的一张表：95% 完整率并不等于核心数据不丢

`completion_rate` 按**任务条数**统计，而 PEAK 里勘查任务只占条数的 2.8%，运维任务占 97.2%。把优先级拆开（`docs/01` §A.3）：

| 策略 | 勘查任务数 | 勘查完成率 | 运维完成率 |
| --- | ---: | ---: | ---: |
| 静态优先级 | 68 | **60.3 %** | 31.8 % |
| FCFS | 68 | 38.2 % | 56.3 % |
| 动态权重 | 68 | **32.4 %** | 97.0 % |
| MLFQ | 68 | 22.1 % | 98.0 % |
| RR | 68 | 17.6 % | 94.5 % |

结论很刺眼，但项目没有回避：

1. 按条数看，动态 / MLFQ / RR 的 92%~96% 远好于静态优先级的 32.6%；
2. 按核心业务看，**静态优先级反而最高（60.3%）**，因为它不为公平性让路；
3. 动态权重的定位是「愿意为运维让路的策略里，勘查完成率最高」，是折中点最优，**不是全面最优**。

这也是页面标题不写「最优调度」的原因。改进方向已经写进文档：按字节加权统计完整率、对 HIGH 任务不做弱网降权、给饥饿硬通道加每轮配额。

## 参数敏感性：静态参数为什么不可靠

固定 PEAK 工况，只改一个参数：

| 对照 | 低优等待 | 低优饥饿率 | 业务完整率 |
| --- | ---: | ---: | ---: |
| MLFQ aging 1500 → 6000 ms | 1.11 → 4.02 s | 0 % | 95.7 → 91.6 % |
| RR 时间片 120 → 500 → 3000 ms | 0.66 → 2.20 → 8.76 s | 0 → 0.2 → 27.0 % | 96.1 → 92.3 → 75.3 % |
| 弱网加剧（`retry_gain` 0.5 → 0.9） | dynamic 1.99 s / mlfq 1.17 s | 0.1 % / 0 % | 93.2 % / 95.2 % |

同一算法换个参数就从 96% 掉到 75%，不存在一个"最好的固定时间片"。**这条实验就是 PDF 痛点④「静态参数固化」的量化证据。**

第三组还记录了一个负面结果：弱网加剧后，动态权重的高优时延反而最高（33.0 s vs MLFQ 28.1 s）——「本地缓存」把弱网任务推迟得更久，抬高了均值。**链路感知在这组实验里没有表现出时延优势**，项目把它原样写进了改进方向。

## GPU：把「跑一次」变成「跑三千次」

Python 参考模型要跑几万次不现实，于是写了 CUDA 分析模型：**一个线程 = 一次完整仿真**，五个策略语义与 Python 版一一对应，所有重复共享共同随机数做配对比较。

RTX 3050 Laptop，`--reps 3000`（单策略 133~313 ms 跑完）：

| 策略 | 吞吐 | 低优平均等待 | 低优饥饿率 | 业务完整率 |
| --- | ---: | ---: | ---: | ---: |
| FCFS | 21.64 | 6.56 s | 8.31 % | 69.26 % |
| RR | 29.78 | 0.80 s | 0.00 % | 95.32 % |
| 静态优先级 | 8.84 | 0.87 s | 0.55 % | 28.30 % |
| 动态权重 | 28.07 | 3.68 s | 0.48 % | 89.79 % |
| MLFQ | 29.69 | 1.58 s | 0.00 % | 94.94 % |

上表为 3000 次均值，95% 置信半宽都很小：吞吐 ≤ 0.13、时延 ≤ 112 ms、饥饿率 ≤ 0.28 个百分点、完整率 ≤ 0.40 个百分点。15000 次仿真约 1.24 秒，约 12097 次/秒。

参数扫描还给出一个反直觉结论：α / β / γ / δ 四因子对业务完整率的影响约 **0.00 个百分点**，而饥饿阈值 `starvation_ms` 的影响高达 **47.8 个百分点**。在 PEAK 过载下，绝大多数低优任务是被「饥饿硬补偿通道」直接救出来的，四因子权重根本没参与决策。所以报告里不该把权重公式当主要卖点——这条写在 `gpu/README.md` 第 5 节。

> GPU 内核是**分析模型**，不是参考模型的逐位复刻（未含离线标定轨迹、任务分片、单机配额、天气扰动）。它只用于策略排序与效应方向的统计推断，不能替代参考模型给绝对指标。

## 多基站 / MEC / 最小 quorum

把单机内核扩成 N 个基站，每站一套独立的线程池、队列与限流器。**接入站 ≠ 算力站**：迁移只搬任务，不改无人机接入点。

| 场景 | 端到端时延 | 完整率 | 站间不均衡度 |
| --- | ---: | ---: | ---: |
| `dynamic` · 纯中心 | 122.7 ms | 95.02 % | 0 |
| `dynamic` · 端-边-云 | 106.4 ms（−13.3 %） | 96.15 % | 1.401 |
| `cross_node` · 端-边-云 | 106.3 ms（−24.3 %） | 95.70 % | 1.399 |
| `dynamic` · 多站-无 MEC | 96.9 ms | 95.21 % | 0.534 |
| `cross_node` · 多站-无 MEC | 124.5 ms | 95.16 % | **0.099** |

- **均衡是有代价的**：`cross_node` 把站间不均衡度从 0.534 压到 0.099（下降一个数量级），代价是 1053 次迁移、平均 519.8 ms，平均等待从 1971 ms 涨到 2190 ms（**+11%**）。
- **端-边-云降时延**：−13.3% / −24.3%，方向一致；MEC 档不均衡度降不下来（1.399）是因为角色硬约束把重勘查钉在中心站，这是设计而非缺陷。
- **一致性哈希再平衡**：加站 3→4 只重映射 28.82%，删站 3→2 是 30.30%，且变化方向全部单调。
- **最小 quorum（教学用，不是 Raft）**：N=3 脑裂 `{1} | {2,3}` 时，少数派完成的 1 个任务被回滚，多数派提交 2 个；恢复后重放，3 个任务一个不丢。

## 3D：真实地形、SSAO 与 120 帧

桌面版不是"网页套壳"，而是 pywebview + 系统 WebView2 的原生窗口，关窗即退，没有地址栏。场景里的地形是**真实 DEM**：

| 项 | 值 |
| --- | --- |
| 数据源 | AWS `elevation-tiles-prod`（Mapzen Terrarium，NASA SRTM 等多源合成，免密钥） |
| 区域 | 辽宁抚顺西露天矿及周边，坑长约 6.6 km，最深处约 −420 m |
| 网格 | 1024 × 760，14.2 m/px，海拔 −281 ~ +237 m，覆盖 14.6 × 10.8 km |
| 优化 | 4 级地形 LOD clipmap（76k 三角形）、真 SSAO、30 架机 482 draw call |
| 天气 | 雨 / 雪 / 沙尘粒子 + 能见度衰减 + 色彩分级，与链路健康度联动 |

按 WebGL 渲染器自动分三档（独显 high / 核显 medium / 软件渲染 cpu），顶栏直接显示实际后端与帧率。RTX 3050 上四场景各采样 12 s：**117.8 ~ 120 fps，P99 11.0 ~ 11.7 ms，掉帧率 0%**；把像素量放大 9 倍仍保持 117.8 ~ 120 fps。

天气不只是视觉：沙尘把链路健康度均值从 42.78 压到 18.02，劣质链路占比 54.0% → 94.4%；同一沙尘批次里，动态权重完成率 92.3%、静态优先级 31.3%，低优饥饿率 0% vs 52.6%。

## 真实数据：采集 → 录制 → 回放

天气线用 Open-Meteo（免费免 key）采集一次快照，之后离线回放，不把小时级气象伪造成秒级动态。

| 项 | 结果 |
| --- | --- |
| 同快照两次回放 | 天气 / 链路 SHA 完全相同 |
| 同快照两次 PEAK × dynamic 吞吐 | 25.4889 / 25.5667，相对差 0.31% |
| 实时采集 vs 快照回放 | 25.9889 / 25.8000，相对差 0.73% |
| 既有同代码抖动基线 | ≤ 1.12% |

默认 `real.enable=false`，15 组矩阵仍走内置合成天气；真实模式只作为独立演示面，界面会标「天气 合成」或「天气 真实 · 观测时间」。

## 诚实的边界

- **核心业务仍未达标**：动态权重的勘查任务完成率只有 32.4%，"95% 完整率"是被 97% 的运维任务抬起来的。
- **动态权重不是全面最优**：PEAK 下高优等待比 MLFQ 更长，弱网加剧时甚至最高；它换的是零饥饿与更少切换。
- 单次实跑有 3~5% 的 wall-clock 抖动，小数位不代表精确值，只看效应方向与量级。
- GPU 内核是分析模型，用于统计推断，不替代参考模型的绝对指标。
- 多站均衡用等待换均衡；MEC 档的站间不均衡是结构性设计。
- 真实数据目前只接了天气，网络探测、轨迹、CPU / 内存动态限流都还没做。
- 项目定位是课程实训与教学演示，不是生产调度器。
