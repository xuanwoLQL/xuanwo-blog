## 一句话

同一份任务轨迹（固定 seed 离线生成），换调度策略各跑一遍，用统一口径的指标证明「多级队列 + 动态权重 + 饥饿补偿 + 限流稳流 + 链路感知」到底改善了什么、代价又是什么。

这是《操作系统》课程实训工程：纯 Python 多线程，没有 asyncio、没有重型框架，核心逻辑只用标准库的 `threading` / `queue` / `concurrent.futures` / `statistics`。

## 四层映射：业务故障 → OS 原理

项目的起点不是「写一个调度算法」，而是五类现场故障。每一类都要先落到操作系统原理，再写成算法，最后拿指标验证。

| 业务现象 | OS 原理 | 算法对策 | 可观测证据 |
| --- | --- | --- | --- |
| 30 架机同时上传，地面站通道被瞬时打满 | 多生产者并发写就绪队列 → 队列溢出 / 背压 | 双队列隔离 + 容量上限 + 满则计数丢弃（不阻塞生产者） | `peak_queue_depth`、`max_high_depth`、`max_low_depth` |
| 心跳、GPS、告警长期传不上去，设备「失联」 | 任务饥饿：低优先级进程等待时间无上界 | 饥饿检测（等待超阈值）+ 硬补偿通道 + 权重倍增 | `starvation_rate_low`、任务级 `wait_ms` 排序 |
| 2 GB 点云排到队首，后面的告警包全被堵住 | 队头阻塞 / 非抢占调度的护航效应 | 时间片 + 真实抢占（未完成回队尾），时间片随拥堵自适应 | `context_switch`、`avg_requeue`、`p95_wait_high_ms` |
| 瞬时峰值把 CPU / IO 打满，服务阻塞 | 资源耗尽 + 缺少并发限流 → 雪崩 | 并发许可 + 非阻塞准入：拿不到许可就留在队列错峰 | `throttle_count`、`overload_seconds`、`running_count ≤ 8` |
| 弱网任务反复重传、抢走通道，好链路反而排不上 | I/O 阻塞未降级 + 设备状态未参与调度 | 链路健康度并入权重；健康度低于 40 降权 0.6；失败的转本地缓存退避 | `retry_rate`、`cached` 计数、`link_sample.health` |

完整 20 行映射（含代码位置与证据表）在仓库的 `docs/04-四层映射对照表.md`。

## 系统怎么搭

| 模块 | 职责 | 关键实现 |
| --- | --- | --- |
| 仿真内核 | 30 个生产者线程按预生成时刻表提交任务，8 个工作线程消费 | `simulator.py`、`station.py` |
| 两级就绪队列 | 高优勘查队列 / 低优运维队列，各自计算拥堵度 | `queue_manager.py` |
| 任务状态机 | `NEW / READY / RUNNING / BLOCKED / CACHED / DONE / DROPPED` | `models.py` |
| 资源限流 | `OK / THROTTLE / REJECT_LARGE / QUOTA` 四种准入结果 | `resource_limiter.py` |
| 链路模型 | 时延、丢包、RSSI 综合成 0~100 健康度，既折算有效带宽，也决定失败概率 | `link_monitor.py` |
| 调度器 | 5 种经典策略 + 1 种跨节点策略，统一接口 | `scheduler/*.py` |
| 落地 | 指标进 MySQL 长表，图表进 `results/`，实验可回放 | `db.py`、`experiment.py`、`visualize.py` |

关键约束是**控制变量**：任务到达与链路质量全部离线预生成为轨迹，5 种策略只是回放同一条输入，服务时长、限流参数和指标口径完全共用。这样策略之间的差异才是算法差异，不是随机数差异。

## 六种调度策略

| 策略 | 一句话 | 在实验里的角色 |
| --- | --- | --- |
| `fcfs` | 全局先来先服务，跨两个物理队列按到达顺序取 | 最公平的基线，用来暴露护航效应 |
| `rr` | 固定 500 ms 时间片，未完成回队尾 | 基线：轮转能救饥饿，但切换开销高 |
| `priority` | 高队列非空则低队列永远轮不到 | 反面教材：刻意复现饥饿 |
| `mlfq` | 分层时间片 300 / 800 ms，低队列等超 1500 ms 可升权 | 经典解法，饥饿率降到 0 |
| `dynamic` | 四因子动态权重 `W = base × (w0 + αQ + βW + γL) × (1 − δS)`，叠加饥饿硬补偿与弱网降权 | 本方案主角 |
| `cross_node` | 在多基站之间做一致性哈希 + 负载感知再平衡 | 能力扩展：站间不均衡度下降一个数量级 |

`dynamic` 的四个因子分别是队列拥堵度 `Q`、已等待时长 `W`、链路健康度 `L` 和系统负载 `S`。拥堵的队列多拿资源，等久的低优任务被补偿，弱网任务降权，系统过载时整体收敛。

## 实验设计：3 工况 × 5 策略

| 项 | 数值 |
| --- | --- |
| 工况 | 轻载日常巡检 / 中载常规勘查 / 高并发峰值勘查 |
| 规模 | 30 架无人机、90 仿真秒、峰值工况 2756 条到达事件 |
| 对照矩阵 | 3 × 5 = 15 组，另有第 6 种策略 `cross_node` 与多站矩阵 |
| 指标 | 24 个统一口径指标；多基站 / MEC 另定义 18 个站级指标键 |
| 数据量 | 15 条 experiment、360 条 exp_metric、14776 条 task_record、1800 条 queue_sample、16604 条 link_sample |

所有组共用同一个 `random.Random(seed)` 顺序消费生成轨迹，测试里直接断言「同 `(code, seed)` 两次生成的轨迹逐元素相同」。

## 结果：不只看均值，还看抖动

仿真依赖真实时钟，同一组实验重复跑有 3~5% 的抖动，单次结果分不清算法差异和运行噪声。于是补了一条 CUDA 分析模型：**一个 CUDA 线程 = 一次完整仿真**，用共同随机数做配对比较。

RTX 3050 Laptop，`--reps 3000`，均值 ± 95% 置信半宽：

| 策略 | 3000 次耗时 | 吞吐（任务/秒） | 低优平均等待 | 低优饥饿率 | 业务完整率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| FCFS | 251 ms | 21.64 ± 0.13 | 6558 ± 112 ms | 8.31 ± 0.28 % | 69.26 ± 0.40 % |
| RR | 285 ms | 29.78 ± 0.03 | 803 ± 13 ms | 0.00 % | 95.32 ± 0.06 % |
| 静态优先级 | 133 ms | 8.84 ± 0.10 | 869 ± 9 ms | 0.55 % | 28.30 ± 0.31 % |
| 动态权重 | 258 ms | 28.07 ± 0.04 | 3680 ± 23 ms | 0.48 % | 89.79 ± 0.15 % |
| MLFQ | 313 ms | 29.69 ± 0.02 | 1580 ± 10 ms | 0.00 % | 94.94 ± 0.03 % |

15000 次仿真约 1.24 秒，约 12097 次/秒，置信区间收窄到 0.1% 量级。

两个结论值得单独写出来：

1. **模型确认通过**：最差策略 `priority` 的吞吐偏差只有 −0.2%，MLFQ 完整率偏差 −1.0%，策略排序与参考模型一致。
2. **参数扫描给了个反直觉结果**：α / β / γ / δ 对业务完整率的影响约 0.00 个百分点，而饥饿阈值 `starvation_ms` 的影响高达 47.8 个百分点。在 PEAK 过载下，绝大多数低优任务是被「饥饿硬补偿通道」直接救出来的，四因子权重根本没参与决策。所以报告里不该把「动态权重公式」当成主要卖点——这条写进了 `gpu/README.md` 第 5 节。

> GPU 内核是**分析模型**，不是参考模型的逐位复刻（未含离线标定轨迹、任务分片、单机配额、天气扰动）。它只用于策略排序与效应方向的统计推断，不能替代参考模型给绝对指标。

## 多基站与 MEC：均衡是有代价的

| 策略 | 模式 | 端到端时延 | 平均等待 | 完整率 | 站间不均衡度 |
| --- | --- | ---: | ---: | ---: | ---: |
| `dynamic` | 纯中心 | 122.7 ms | 2139 ms | 95.02 % | 0 |
| `dynamic` | 端-边-云 | 106.4 ms（−13.3 %） | 1842 ms | 96.15 % | 1.401 |
| `cross_node` | 纯中心 | 140.5 ms | 2071 ms | 94.93 % | 0 |
| `cross_node` | 端-边-云 | 106.3 ms（−24.3 %） | 1864 ms | 95.70 % | 1.399 |
| `dynamic` | 多站-无 MEC | 96.9 ms | 1971 ms | 95.21 % | 0.534 |
| `cross_node` | 多站-无 MEC | 124.5 ms | 2190 ms | 95.16 % | **0.099** |

- **端-边-云降端到端时延**：−13.3% / −24.3%，两次方向一致。
- **`cross_node` 的价值在多站-无 MEC 档最清楚**：站间不均衡度 0.534 → 0.099，同一代码两次运行在 0.02~0.10 波动，稳定结论是「下降一个数量级」。
- **代价必须一起写**：1053 次迁移、平均迁移代价 519.8 ms，平均等待从 1971 ms 涨到 2190 ms（约 +11%）。均衡度是用等待换来的。
- **端-边-云档不均衡度降不下来（1.399）**：MEC 角色硬约束把重勘查任务钉在中心站，站间负载结构性地分开，这是设计要求，不是缺陷。

另外补了一致性哈希再平衡（增删站只迁约 1/N 的键）和分区期间的最小 quorum 共识，都用测试覆盖了脑裂、节点宕机与分区恢复。

## 可观测性：把调度过程摊开

### 3D 仿真场景

真实 DEM 地形、SSAO、地形 LOD、雨 / 雪 / 沙尘天气、无人机模型与链路连线。链路颜色随健康度变化，地面站负载圈层由绿到红，队列深度和系统负载在底部实时画曲线。

### OS 微观透视镜

![OS 微观透视：两级就绪队列传送带，方块大小=数据量、颜色=任务类型、红条=饥饿倒计时](/images/projects/uav-sched-sim/os-inspector.jpg)

| 页签 | 看什么 |
| --- | --- |
| 线程 | 30 架机 = 30 个线程，五态色块、绑核 `C0~C7`、当前任务、等待与切换间隔 |
| 队列 | 两级队列的传送带，方块大小是数据量，颜色是任务类型，底部红条是饥饿倒计时 |
| 权重 | 四因子雷达 + 高 / 低候选的权重天平，标出「饥饿提权 / 弱网降权」 |
| 混沌 | 弱网风暴 / 并发洪峰 / 死锁注入 + 看门狗回收计数 |
| 回放 | 600 帧环形缓冲拖动复盘，Trace 可导出 JSON / CSV |

三个混沌注入都做了真实现：弱网风暴把选中 40% 的无人机 `p_fail × 2.5`；并发洪峰一次塞 500 个高优任务，实测高优队列冲到 507、系统负载 348、限流触发；死锁注入后看门狗 3 仿真秒判定并强制回收。

### 仿真结果界面

![仿真结果界面：按目录分组的实验图表，每张标生成时间与文件大小](/images/projects/uav-sched-sim/results.jpg)

五个页签把图表、15 组矩阵、时序回放、置信区间放在一个遮罩里，不用再翻文件夹找图：

界面上还能一键重跑实验、对比两份明细、导出报告素材包（zip 里自动生成 `结论摘要.md`）。`/results_img` 这类会读本地磁盘的接口做了白名单目录 + 图片扩展名双闸，`../`、绝对路径、非图片一律 404，测试里有 7 个目录穿越反例。

## 真实环境数据

天气线走「采集 → 录制 → 回放」：Open-Meteo 免费免 key 采集一次快照，之后离线回放，不把小时级气象伪造成秒级动态。

| 项 | 结果 |
| --- | --- |
| 同快照两次回放 | 天气 / 链路 SHA 完全相同 |
| 同快照两次 PEAK × dynamic 吞吐 | 25.4889 / 25.5667，相对差 0.31% |
| 实时采集 vs 快照回放 | 25.9889 / 25.8000，相对差 0.73% |
| 既有同代码抖动基线 | ≤ 1.12% |

默认 `real.enable=false`，所以 15 组矩阵与既有基线仍走内置合成天气；真实模式只作为独立演示面，顶栏和结果界面会标「天气 合成」或「天气 真实 · 观测时间」。

## 快速开始

```bash
git clone https://github.com/xuanwoLQL/uav-sched-sim.git
cd uav-sched-sim

python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt

# 自检 + 三工况标定（只读，几秒）
.venv/Scripts/python run.py check
.venv/Scripts/python run.py calibrate

# 跑全量 15 组，出图和 CSV
.venv/Scripts/python run.py all

# 打开 3D 实时可视化
.venv/Scripts/python run.py ui
```

MySQL 是可选的：连不上时实验仍然跑完，只是不入库。要入库就先复制 `config.example.yaml` 为 `config.yaml`，口令只放在本地或环境变量里。

## 诚实的边界

- 单次实跑有 3~5% 的 wall-clock 抖动，小数位不代表精确值，只看效应方向与量级。
- GPU 内核是分析模型，用于统计推断，不替代参考模型的绝对指标。
- `cross_node` 用等待换均衡，MEC 档的站间不均衡是结构性设计。
- 真实数据目前只接了天气，网络探测、轨迹、CPU / 内存动态限流都还没做。
- 项目定位是课程实训与教学演示，不是生产调度器。
