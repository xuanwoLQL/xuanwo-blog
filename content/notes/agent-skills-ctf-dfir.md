> 本文只讨论授权 CTF、线下靶场和应急演练环境。Agent 可以加速检索与整理，但不能替代授权边界、人工验证和现场判断。

我一开始只是把提示词、命令和踩坑记录堆在一个 Markdown 文件里。文件越写越长，问题也越来越明显：同一个规则在 Claude Code、Codex 和其他运行时里各复制一份；模型不知道什么时候该读哪一段；一次加载全部内容又会把上下文塞满。

后来我把它改成了一套更接近软件的 Agent Skills：

- 每个技能只有一个源目录；
- 由适配层把同一份源挂到不同运行时；
- 用短路由决定「先读哪一段」；
- 把工具能力拆成只读检索和受控执行；
- 每次修改都跑 smoke test，而不是凭感觉觉得「应该能用」。

这篇文章记录这套结构的设计取舍。

## 1. Prompt 合集为什么会失控

把安全流程写成 prompt 很直接，但一旦进入真实比赛，会遇到四个问题：

| 问题 | 表现 | 后果 |
| --- | --- | --- |
| 入口不唯一 | 每个运行时各维护一份提示词 | 版本漂移 |
| 内容全量加载 | 一开场就塞入渗透、应急、工具、脚本说明 | 上下文被无关内容占满 |
| 路由模糊 | 把 CTF 单题和授权靶场实战混在一起 | 模型给错方法论 |
| 工具没有边界 | 搜索、执行、平台写接口混成一个工具 | 误操作风险变高 |

所以我没有继续扩写一个「超级提示词」，而是把它拆成 Skill、路由和适配层三部分。

## 2. 单源多运行时

稳定结构可以概括为：

```text
agent-skill/
├─ skills/
│  ├─ ctf-0day/
│  │  ├─ SKILL.md
│  │  ├─ 知识库/
│  │  ├─ 外部参考/
│  │  └─ scripts/
│  └─ ctf-solver/
│     ├─ SKILL.md
│     ├─ 深度文章/
│     ├─ WP 索引/
│     └─ 常用脚本/
├─ mcp/
│  └─ servers/
├─ adapters/
├─ install/
└─ README.md
```

核心原则是 **single source, many adapters**：

- `skills/` 是唯一内容源；
- `adapters/` 只负责路径、加载方式和 MCP 配置差异；
- `install/` 只做挂载，不复制正文；
- 运行时的目录只是入口，不成为第二份真源。

这样一来，改一次 `SKILL.md`，所有运行时看到的内容就同步变化，不需要手工对四份文件做 diff。

## 3. 两个技能，三种问题

安全 Agent 最容易犯的错，是把「解一道题」和「打一张靶场」混成同一种任务。

我把能力路由分成两类：

| 任务 | 技能 | 典型输入 | 输出 |
| --- | --- | --- | --- |
| 授权靶场实战、内网、提权、应急响应 | `ctf-0day` | 靶机、网段、日志、内存镜像、流量包 | 攻击路径、排查过程、flag 或取证结论 |
| 经典 CTF 单题、找同类题、找脚本 | `ctf-solver` | 题面、附件、可疑文件、编码题 | payload、脚本、同类 WP、解题思路 |

边界不是文字游戏，而是为了避免错误迁移：

- 面对被入侵机器，不应只套用「CTF 单题」的 payload 模板；
- 面对一道 Web 附件题，也不需要先启动完整的渗透链路；
- 线上真实资产不在两类技能的目标范围内。

路由写清楚之后，模型第一分钟就能做出正确的资源选择，而不是在海量 Markdown 里翻找。

## 4. Skill 文件应该短，知识按需读取

`SKILL.md` 的职责不是装下所有知识，而是回答三个问题：

1. 我在什么条件下被触发？
2. 我第一步做什么？
3. 需要更细的内容时，按什么顺序读取？

一个可读的骨架大致如下：

```markdown
---
name: ctf-solver
description: "经典 CTF 单题解题知识库。用于题面、附件、payload、同类 WP 和现成脚本检索；不用于授权靶场实战或线上真实资产。"
---

# CTF 解题知识库

## 先读索引
1. AI-SEARCH-INDEX.md
2. PAYLOAD-CHEATSHEET.md
3. 按题型读取对应深度文章

## 输出格式
- 先给结论
- 再给复现命令
- 最后写验证方式与失败分支

## 边界
- 只处理公开 CTF 题或明确授权环境
- 不把示例 payload 直接指向线上真实资产
```

真正的知识库可以是几 MB、几千个文件，但入口必须足够短。模型应该像查手册一样按需读取，而不是每次把所有手册背一遍。

## 5. MCP 工具：只做两件事

工具层只有两个接口：

| 工具 | 作用 | 安全设计 |
| --- | --- | --- |
| `kb_search` | 检索核心库、外源库或合并索引 | 只读，不执行目标命令 |
| `run_weapon` | 调用技能目录内的受控脚本 | 限定目录、限定脚本类型、限制参数与超时 |

这里我刻意没有加入平台写接口：

- 不自动开环境；
- 不提交 flag；
- 不读取平台 token；
- 不把比赛控制面交给模型。

这不是「模型不会用」，而是权限设计：Agent 可以帮助分析、生成和验证，但比赛平台上的关键动作必须由人确认。

### 路径约束

`run_weapon` 至少要做到：

- 只允许调用预设脚本目录；
- 拒绝 `..`、绝对路径和符号链接逃逸；
- 只允许预期扩展名；
- 设置执行超时和输出上限；
- 对每条调用记录参数摘要，不记录敏感 token。

这些约束看起来琐碎，但它们决定了一个工具是「助手」还是「不可控执行器」。

## 6. 不能只写规则，要有验收

技能套件最怕写完文档没有测试。我给 MCP 层加了 smoke test，至少验证：

- 能否完成初始化；
- 工具列表是否只有预期接口；
- 平台接口纪律是否仍然存在；
- `kb_search` 的核心库、外源库和合并模式是否可用；
- `run_weapon` 是否能正常执行白名单脚本；
- 路径越界请求是否会被拒绝。

这比在 README 里写一句「已测试」可靠得多。

博客本身也采用了同样的思路：

```text
Hugo build
  → 内部链接检查
  → 首页统计 / meta / OG / CSP 质量检查
  → 部署前阻断
```

内容和工具都需要可验证的门槛，才能避免「本地看起来对，线上还是旧版」。

## 7. 从提示词到工程化，真正改变的是什么

### 7.1 上下文更稳定

入口文件短，知识按需加载，模型不会在无关工具说明里迷路。

### 7.2 行为更可预测

触发条件、输出格式和边界写在技能开头，不同会话不必靠用户重复解释。

### 7.3 能力更容易迁移

Claude Code、Codex 或其他运行时只是适配层不同；技能正文和验收逻辑保持同一份。

### 7.4 安全边界更清楚

只读检索、受控执行、人工提交，把「能做什么」和「不能自动做什么」分开。

## 8. 面试时怎么讲

如果面试官问「你的 Agent 项目有什么技术含量」，可以从四个层次回答：

1. **内容层**：如何把 CTF、渗透和应急知识拆成可检索的索引与深度文章；
2. **路由层**：如何区分授权靶场、单题求解和线上真实资产；
3. **工具层**：如何用 MCP 封装只读检索和受控执行；
4. **工程层**：如何处理运行时差异、路径越界、版本漂移和 smoke test。

这比说「我写了几个提示词」更接近真实工程。

## 9. 后续

我还会继续补三块：

- 给知识库增加来源、更新时间和可信度字段；
- 把常用验证脚本统一成可复现的测试样例；
- 在公开仓库中补一份不含本地路径和敏感信息的最小演示版。

Agent Skills 真正有价值的地方，不是让模型「多知道一点」，而是让它在一个可解释、可验证、可回滚的流程里工作。

## 本地验收命令

技能目录至少应能通过结构检查：

```bash
test -f skills/ctf-0day/SKILL.md
test -f skills/ctf-solver/SKILL.md
rg -n '^name:|^description:' skills/*/SKILL.md
```

MCP 冒烟测试：

```bash
python mcp/tests/smoke_test_awd_mcp.py
```

安全边界检查：

```bash
rg -n 'token|submit|open_env|flag' mcp/servers
```

发现工具接口出现平台写能力时，先停用并审计，不要为了自动化牺牲边界。
